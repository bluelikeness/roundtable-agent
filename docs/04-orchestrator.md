# 멀티봇 오케스트레이터 설계

> 작성일 2026-11-08

## 1. 역할과 범위

오케스트레이터는 `claude -p`로 뜨는 Claude Code 세션이다. 사용자 메시지를 읽고 어떤 봇을 어떤 순서로 부를지 정하고, 봇 원문은 손대지 않고 그대로 두되 그 아래 자기 정리를 붙이고, 봇이 되묻거나 확정을 요구하면 사용자에게 돌린다. 이 문서는 그 행동을 시스템 프롬프트와 규칙으로 고정한다.

**하는 일**

- 사용자 의도 해석 → 모드(단독·단일·팬아웃·릴레이·토론) 결정
- 봇 선택: 툴 description과 `status`로 판단, 사용자 지명이 있으면 그대로
- 릴레이 시 앞 봇 답을 뒤 봇이 이해할 질문으로 변환
- 봇 원문을 인용하지 않고 비교·요약·추천을 자기 말로 작성
- 되물음·확정 요구를 사용자에게 전달하고 실행 종료

**하지 않는 일**

- 봇 원문 수정·요약 후 원문 폐기 (원문은 `tool_result`로 그대로 UI에 간다)
- 결제·예약 확정 버튼을 사용자 확인 없이 누르기
- 파일·셸·웹 접근 (툴 화이트리스트로 차단됨)
- 봇 가용성 판단을 추측으로 하기 (`status` 툴이 있다)

**입력**: 사용자 메시지, 이전 턴 맥락(`--resume`), 가용 봇의 `ask`·`status` 툴. **출력**: stream-json 이벤트(툴 호출, 중간 노트, 최종 정리).

## 2. 모드 판단

모드는 사용자가 고르지 않는다. Claude가 아래 순서로 판단하고, 판단 결과를 첫 중간 노트에 한 줄로 밝힌다.

> 그림: 모드 결정 흐름 · 질문 4개, 모드 5개 (원본은 claude.ai 문서에만 있음)

| 모드 | 트리거 예 | 툴 호출 패턴 |
| --- | --- | --- |
| 단독 답변 | "너는 어떻게 동작해?", "아까 답 정리해줘" | 없음 |
| 단일 봇 | "강남 한식 예약 가능한 곳 찾아줘" | `ask` 1회, description에 가장 맞는 봇 |
| 팬아웃 | "셋 다한테", "각각 물어봐", "누가 더 잘 찾나" | 가용 봇 전부에 `ask` 병렬 |
| 릴레이 | "Vooy가 찾은 걸 뮤즈한테 확인시켜", "A 결과로 B가 예약" | `ask` A → 변환 → `ask` B 순차 |
| 주고받기(토론·회의·게임) | "서로 비판하게", "둘이 합의 볼 때까지", "회의해", "의견 주고받아", "끝말잇기 해" | 정해진 절차 없음. Claude가 사회자로서 요청의 목적을 읽고 매 답마다 다음 수(누구에게·무엇을)를 정한다. 라운드 상한·시간만 고정 |

팬아웃에서 "가용 봇 전부"는 질문과 무관한 봇을 빼는 것을 허용한다. 단, 뺀 이유를 노트에 적는다("피클은 한국 예약에 맞지 않아 제외"). 질문이 모호하면 봇을 부르기 전에 사용자에게 되묻는 것보다, 가장 그럴듯한 해석으로 진행하고 해석을 노트에 적는다. 봇 응답이 느려서 왕복 한 번이 비싸기 때문이다.

## 3. 봇 선택 규칙

우선순위 순서다. 위 규칙이 결정하면 아래는 보지 않는다.

1. **사용자 지명**: 메시지에 봇 이름(Vooy·부이, 뮤즈·Muse, 피클·Pickle, 또는 설정의 별칭)이 있으면 그 봇만. "셋 다"·"전부"·"다른 봇도"는 가용 봇 전부.
2. **직전 맥락**: "아까 그 봇", "다시 물어봐"처럼 이전 턴을 가리키면 마지막으로 호출한 봇.
3. **가용성**: `mcp.json`에 없는 봇은 존재하지 않는다. 있어도 `status.available=false`면 부르지 않고 노트에 이유를 적는다. `status`는 비용이 싸므로 팬아웃 전에 한 번씩 호출한다.
4. **description 적합도**: 툴 description의 "잘하는 일·못하는 일·언어"와 질문을 대조. 한국 서비스 예약·주문·정부 민원은 Vooy·피클, 영어권 웹·쇼핑·이메일은 뮤즈 쪽으로 기운다. 동률이면 `avg_latency_ms`가 짧은 봇.
5. **그래도 모호하면** 단일 봇이 아니라 팬아웃으로 간다. 틀린 봇 하나보다 비교 가능한 둘이 낫다.

**지명 해석 예**

| 사용자 말 | 해석 |
| --- | --- |
| "Vooy한테 물어봐" | Vooy 단일 |
| "Vooy랑 피클한테" | Vooy·피클 팬아웃 |
| "Vooy 말고" | Vooy 제외한 가용 봇 전부 |
| "Vooy가 찾은 거 뮤즈가 확인" | Vooy → 뮤즈 릴레이 |
| "피클은 빼고 둘이 토론" | 나머지 둘 토론 |

봇 이름 별칭은 허브가 시스템 프롬프트에 주입한다(`{{bot_aliases}}`). 프롬프트에 봇 이름을 하드코딩하지 않는다.

## 4. 릴레이 입력 변환

뒤 봇은 앞 봇의 존재를 모른다. Claude가 앞 봇 답을 뒤 봇이 바로 행동할 수 있는 요청으로 다시 쓴다.

**규칙**

- 앞 봇 원문을 통째로 붙이지 않는다. 뒤 봇이 필요한 사실(장소·시간·가격·URL·선택지)만 뽑는다.
- 출처를 밝힌다: "다른 AI 비서가 찾은 결과인데"처럼. 뒤 봇이 자기가 한 일로 착각하지 않게.
- 요청 동사를 명확히: "확인해줘", "예약해줘", "더 싼 대안 찾아줘". 앞 봇 답을 그냥 전달하면 뒤 봇은 할 일을 모른다.
- 사용자의 원래 제약(인원·날짜·예산)을 매 단계 다시 넣는다. 봇은 허브 세션을 모른다.
- 1,000자 넘으면 요약한다. 봇 입력창 한계와 응답 품질 때문.

**예시**

| 단계 | 내용 |
| --- | --- |
| 사용자 | "Vooy가 찾은 강남 한식집을 뮤즈한테 예약 가능한지 확인시켜. 내일 저녁 7시 2명" |
| Vooy 원문 | "강남 근처 한식집 3곳 찾았어요. 1) 한옥집 (테라스, 1인 3만원) 2) 밥상 (예약 필수) 3) 소반 (웨이팅 많음) \[버튼: 1번 예약\] \[버튼: 2번 예약\]" |
| Claude → 뮤즈 | "다른 비서가 추천한 서울 강남 한식당 세 곳의 내일 저녁 7시 2명 예약 가능 여부를 확인해줘: 한옥집, 밥상, 소반. 가능한 곳과 예약 방법(전화·네이버·캐치테이블)을 알려줘. 예약은 아직 하지 마." |
| 뮤즈 원문 | "밥상은 7시 가능, 한옥집은 7시 30분부터, 소반은 예약 안 받음" |
| Claude 정리 | 세 곳 표 + "밥상이 조건에 맞습니다. 예약할까요? (Vooy 버튼 또는 뮤즈로 진행 가능)" |

"예약은 아직 하지 마"처럼 행동 범위를 매번 명시한다. 봇들은 스스로 결제까지 가려는 성향이 있다.

**토론 변환**(예시, 고정 형식 아님 — 아래 "주고받기 진행"): 봇 B에게 보내는 메시지는 예컨대 "다른 비서는 X를 추천했고 이유는 Y야. 네 추천 Z와 비교해 어느 쪽이 더 나은지, 상대 안의 약점이 뭔지 말해줘" 형태. 매 라운드 사용자 제약을 반복하고, 이전 라운드 전문은 넣지 않는다.

**주고받기 진행** (2026-11-12 개정: 고정 절차 → Claude 판단)

처음엔 "1라운드 동시에 각자 의견 → 2라운드부터 다른 봇 주장을 한 줄씩 전하고 동의·반대를 묻는다"는 절차를 프롬프트에 박았다. 실사용(성선설·성악설 토론)에서 봇들이 각자 하고 싶은 말만 했다. 동시에 부르니 상대의 직전 발언이 아니라 한 라운드 전 요약에 답했고, "동의·반대를 말해줘"라는 막연한 요청은 자기 주장 재정리만 낳았다. 끝말잇기·보고 취합처럼 요청마다 맞는 진행이 다르므로, 절차 대신 사회자의 목적과 판단 기준을 준다.

- 요청의 목적을 먼저 읽는다. 토론은 의견이 부딪혀 근거의 강약이 드러나는 것, 회의는 갈린 지점을 좁혀 하나로 정하는 것, 게임은 규칙대로 이어 가는 것.
- 봇 답마다 다음 수를 정한다. 토론이면 보통 차례로 부르고, 상대의 가장 센 주장을 그 봇의 문장으로 짧게 인용해 거기에 답하게 한다. 피한 질문은 다시 묻는다.
- 봇 차례 사이 노트 한 줄(쟁점·다음에 누구에게 무엇을 왜)로 진행이 화면에 보이게 한다.
- 정리에는 오간 내용 위에 Claude의 판단(반박을 견딘 주장, 진짜 갈린 지점, 틀리거나 미확인인 사실)을 쓴다.
- 고정 제약만 남긴다: 봇당 발언 {{debate_max_rounds}}회, 누적 예상 480초(러너 600초), 실패 봇 제외, 직전과 똑같은 답은 새 답으로 다루지 않음.

## 5. 되물음·확정 단계 처리

봇이 되물으면(`needs_input=true`) Claude는 세 갈래 중 하나를 고른다.

| 상황 | 행동 |
| --- | --- |
| 답이 사용자 메시지나 세션 맥락에 있다 (인원·날짜·지역) | 즉시 `ask`로 답한다. 노트에 "Vooy가 인원을 물어 2명으로 답함"을 남긴다 |
| 답이 맥락에 없지만 합리적 기본값이 있다 (시간대 선호 없음 → "상관없음") | 기본값으로 답하고 노트에 적는다. 단, 돈·날짜·장소처럼 틀리면 비용이 드는 항목은 기본값을 넣지 않는다 |
| 답을 사용자만 안다 | 봇의 질문을 그대로 전달하고 실행을 끝낸다. 다음 메시지에서 사용자 답을 받아 해당 봇에 이어 보낸다 |

되물음 왕복은 봇당 최대 2회. 넘으면 "봇이 계속 추가 정보를 요구해 멈췄습니다"로 사용자에게 넘긴다.

**확정 단계** (`structured.confirmation_required`가 있거나 원문이 결제·예약 확정·전송·구매를 묻는 경우)

- 절대 자동으로 넘기지 않는다. `[tap:]`으로 확정 버튼을 누르는 것도 금지.
- 최종 정리에 확정 내용(무엇을·언제·얼마에)을 눈에 띄게 적고 "진행할까요?"로 끝낸다.
- 사용자가 다음 메시지에서 "진행해"라고 하면 그때 `[tap:<action_id>]` 또는 "확정해줘"를 보낸다. `action_id`는 직전 응답 것만 유효하니 두 턴 지났으면 봇에게 다시 상황을 물어 새 `action_id`를 받는다.
- 사용자가 미리 "확인 없이 결제까지 해"라고 했어도 금액이 설정 상한(`{{auto_confirm_limit}}`, 기본 0원)을 넘으면 묻는다.

**봇 실패** (`ok=false`): 재시도는 어댑터가 이미 했으니 Claude는 재시도하지 않는다. 다른 가용 봇이 같은 일을 할 수 있으면 노트에 밝히고 그 봇에 보낸다. 없으면 실패를 정리에 적는다. 팬아웃 중 일부 실패는 나머지로 정리를 완성한다.

## 6. 종료 조건과 턴 예산

한 실행은 아래 중 먼저 오는 조건에서 끝난다.

| 조건 | 설명 |
| --- | --- |
| 목적 달성 | 모드가 요구한 호출이 끝나고 정리를 썼다 |
| 사용자 입력 필요 | 되물음 전달 또는 확정 요청 |
| 토론 종료 | 봇들이 같은 결론에 이르렀거나, 새 정보 없이 반복되거나, 라운드 상한(기본 3) 도달 |
| 턴 예산 소진 | `--max-turns 12`. 11턴째에 도달하면 호출을 멈추고 지금까지로 정리한다 |
| 전체 타임아웃 | 러너가 600초에 SIGTERM. Claude는 관여 못 하므로 긴 작업은 봇당 `timeout_s`를 120 이하로 유지(실제 작업 요청만 180) |

**툴 호출 예산 (모드별 목표)**

| 모드 | `status` | `ask` | 합계 |
| --- | --- | --- | --- |
| 단일 | 0\~1 | 1 (+되물음 2) | ≤ 4 |
| 팬아웃 (3봇) | 3 | 3 (+되물음) | ≤ 8 |
| 릴레이 (2단) | 2 | 2 (+되물음) | ≤ 6 |
| 토론 (2봇 × 3라운드) | 2 | 6 | ≤ 10 |
| 회의 (4봇 × 2\~3라운드) | 4 | 8\~12 | ≤ 16 (Claude 턴은 라운드당 1) |

토론은 예산이 가장 크므로 라운드 상한을 사용자가 늘리려 해도 5를 넘기지 않는다. 토론 라운드 수는 설정(`{{debate_max_rounds}}`)으로 주입한다.

## 7. 출력 형식

Claude의 텍스트 출력은 두 종류다. 러너는 둘을 구분하지 않고 `claude.note`(중간)·`claude.final`(마지막)로만 나눈다.

**중간 노트** — 툴 호출 사이에 한두 줄. 사용자가 진행 상황을 읽는 용도.

- 첫 노트: 모드와 봇 선택 이유. "비교 요청이라 Vooy·뮤즈에 동시에 묻습니다. 피클은 한국 예약에 맞지 않아 제외."
- 릴레이 단계: "Vooy가 찾은 3곳을 뮤즈에 넘겨 예약 가능 여부를 확인합니다."
- 되물음 자동 응답: "Vooy가 인원을 물어 2명으로 답했습니다."
- 봇 제외·실패: "뮤즈는 로그인 만료로 응답 불가."

봇 원문은 노트에 다시 쓰지 않는다. 이미 `tool_result`로 UI에 있다.

**최종 정리** — 마지막 텍스트 블록. 구조 고정.

1. 결론 한 줄 (추천 또는 상태). 팬아웃이면 "누가 뭘 찾았고 어느 게 나은지".
2. 비교 (팬아웃·토론일 때만): 봇 × 항목 표. 항목은 질문에 맞게(가격·시간·조건·신뢰도).
3. 주의: 봇 간 모순, 확인 안 된 정보, 실패한 봇.
4. 다음 행동: 확정이 필요하면 "진행할까요?", 되물음이면 봇의 질문, 아니면 가능한 후속 요청 1\~2개.

길이: 단일 모드 5줄 이내, 팬아웃·토론 15줄 이내. 봇 원문을 인용하지 않는다 ("Vooy에 따르면 …" 식 요약은 가능).

**언어**: 사용자 메시지 언어. 봇에 보내는 메시지는 봇 description의 언어(한국어 봇에는 한국어, 뮤즈에는 영어가 더 정확하면 영어).

## 8. 시스템 프롬프트 초안

`orchestrator.md`로 저장해 `--append-system-prompt-file`로 주입한다. `{{ }}`는 러너가 실행 직전에 채운다. Claude Code 기본 프롬프트 뒤에 붙으므로 첫 줄에서 역할을 덮어쓴다.

```markdown
# 역할

너는 코딩 도구가 아니라 여러 AI 비서(봇)를 대신 부려주는 오케스트레이터다.
파일·셸·웹 도구는 없다. 쓸 수 있는 도구는 봇별 `mcp__<봇>__ask`와 `mcp__<봇>__status`뿐이다.
사용자는 한 명이고 너와 봇들의 대화를 웹 화면에서 실시간으로 본다.
봇 원문은 도구 결과로 이미 화면에 표시되므로 너는 원문을 반복하지 말고 판단·정리만 한다.

# 봇

지금 쓸 수 있는 봇과 별칭: {{bot_aliases}}
각 봇이 잘하는 일·응답 시간·언어는 `ask` 도구 설명에 있다. 설명을 읽고 고른다.
봇은 서로를 모르고 이 대화도 모른다. 봇에게 보내는 메시지에는 필요한 맥락(인원·날짜·장소·예산)을 매번 넣는다.

# 모드 판단 (위에서부터)

1. 봇 없이 답할 수 있는 질문(네 동작, 이전 답 정리)이면 봇을 부르지 않는다.
2. 사용자가 봇을 지명했으면 그대로. "둘 다/셋 다"는 팬아웃, "A 결과를 B에"는 릴레이. 토론·회의·봇끼리 게임은 "봇끼리 주고받게 할 때"대로 Claude가 진행. 봇을 지명하지 않았으면 가용 봇 전부.
3. 비교·여러 의견을 원하면 가용 봇에 동시에 묻는다(팬아웃). 질문과 무관한 봇은 빼고 이유를 적는다.
4. 앞 봇 답이 뒤 봇 입력으로 필요하면 순서대로 부른다(릴레이).
5. 그 외에는 가장 적합한 봇 하나. 모호하면 하나를 추측하지 말고 팬아웃.

# 호출 규칙

- 팬아웃 전에 각 봇의 `status`를 확인한다. `available=false`면 부르지 않고 이유를 적는다.
- `thread_id`는 항상 `{{session_id}}`.
- `timeout_s`는 기본값. 봇이 실제 작업(예약·주문)을 하는 요청만 180.
- 릴레이에서 뒤 봇에 보낼 때: 앞 봇 원문을 붙이지 말고 필요한 사실만 뽑아, "다른 비서가 찾은 결과"라고 출처를 밝히고, 할 일을 동사로 명확히 쓰고, 행동 범위("예약은 아직 하지 마")를 명시한다.
- 토론·회의에서 한 봇이 말하는 횟수는 최대 {{debate_max_rounds}}번(라운드 상한). 진행은 `runner/orchestrator.md` "봇끼리 주고받게 할 때"(사회자 판단, 절차 없음).
- 도구 결과의 `ok=false`는 봇 실패다. 네가 재시도하지 않는다. 다른 봇이 할 수 있으면 넘기고, 아니면 정리에 실패로 적는다.

# 되물음과 확정

- 도구 결과 `needs_input=true`면 봇이 되물은 것이다. 답이 대화에 있으면 바로 답하고, 틀려도 비용이 없는 항목은 합리적 기본값으로 답하되 노트에 적고, 돈·날짜·장소처럼 사용자만 아는 것은 봇의 질문을 사용자에게 전달하고 멈춘다. 봇당 되물음 왕복은 2회까지.
- 도구 결과에 `confirmation_required`가 있거나 봇이 결제·예약 확정·전송·구매를 물으면 절대 진행하지 않는다. `[tap:]`으로 확정 버튼을 누르지도 않는다. 확정 내용(무엇·언제·얼마)을 정리에 적고 "진행할까요?"로 끝낸다. 사용자가 다음 메시지에서 허락하면 그때 진행한다.
- 자동 확정 상한: {{auto_confirm_limit}}원. 사용자가 미리 허락했어도 이 금액을 넘으면 묻는다.

# 출력

- 도구를 부르기 전에 한 줄 노트: 어떤 모드로 어떤 봇을 왜 부르는지.
- 단계가 바뀔 때 한 줄 노트. 봇 원문을 노트에 옮기지 않는다.
- 마지막에 정리: ① 결론 한 줄 ② 비교표(팬아웃·토론일 때만, 봇×항목) ③ 주의(모순·미확인·실패) ④ 다음 행동(확정 질문 / 봇의 되물음 / 후속 제안). 단일 모드 5줄, 그 외 15줄 이내.
- 사용자 언어로 쓴다. 봇에게는 그 봇의 언어로 보낸다.
- 봇 이름은 사용자가 쓴 표기(별칭)를 따른다.

# 금지

- 봇 원문을 수정·요약해 원문인 것처럼 쓰기
- 확인 없이 돈이 드는 행동
- 가용성 추측 (`status`가 있다)
- 턴이 {{max_turns}}에 가까워지면 더 부르지 말고 지금까지로 정리
```

주입 변수: `bot_aliases` (허브 `bots.yaml`에서), `session_id`, `debate_max_rounds` (기본 3), `auto_confirm_limit` (기본 0), `max_turns` (러너 설정과 동일). 봇 목록·설명은 변수로도 넣지 않는다. MCP 툴 description이 단일 출처다.

## 9. 세션 분할과 요약 주입, 비용

**세션 분할**: 허브 세션은 영구지만 Claude Code 세션은 `--resume`으로 이어질수록 컨텍스트가 커져 비용과 지연이 늘고, 봇 원문(`tool_result`)이 쌓이면 특히 빠르다. 러너는 다음 조건에서 새 Claude Code 세션을 만든다.

- 마지막 메시지 후 24시간 경과
- 누적 `tool_call` 20건 초과 (대략 원문 20개)
- 사용자가 "새로 시작" 명령

**요약 주입**: 새 세션의 첫 메시지 앞에 러너가 `<session_summary>`를 붙인다. 내용은 직전 세션의 마지막 `claude.final` 전문 + 각 봇의 마지막 원문 300자 + 미해결 확정 건(있으면). Claude가 아니라 러너가 기계적으로 조립한다. 추가 Claude 호출 없이 끝내기 위해서다.

```
<session_summary>
이전 대화 요약(허브가 자동 생성):
- 마지막 정리: ...
- Vooy 마지막 응답(일부): ...
- 대기 중 확정: 밥상 내일 19:00 2명 예약 (action_id 만료됨, 다시 요청 필요)
</session_summary>

(사용자 메시지)
```

봇 쪽 대화 스레드(`thread_id`)는 그대로 유지된다. 봇은 자기 맥락을 갖고 있으므로 Claude만 새 세션이 돼도 이어진다.

**비용 추정** (구독 한도 기준, Sonnet)

| 모드 | 입력 토큰(대략) | 출력 토큰 | 메시지당 |
| --- | --- | --- | --- |
| 단일 | 프롬프트 2k + 맥락 2\~10k + 원문 0.5k | 0.3k | 작음 |
| 팬아웃 3봇 | 위 + 원문 1.5k + status 3회 | 0.6k | 중간 |
| 토론 2봇 3라운드 | 위 + 원문 6회 누적(매 턴 재입력) | 1.2k | 큼 — 단일의 5\~8배 |

세션이 길어질수록 "맥락" 항목이 전부를 지배한다. 24시간·20건 분할 규칙이 비용 제어의 핵심이고, 토론은 하루 몇 번 수준으로만 쓰는 전제다. 실제 수치는 `run.usage`로 집계해 첫 주 뒤 분할 기준을 조정한다.

## 10. 테스트 시나리오

Mock 어댑터 2\~3개(`mock-a`: 식당·예약, `mock-b`: 여행·항공, `mock-c`: 영어 전용 쇼핑)로 `claude -p`를 실제 실행해 검증한다. 합격 기준은 stream-json에서 기계적으로 확인한다.

| # | 입력 | 기대 툴 호출 | 기대 정리 |
| --- | --- | --- | --- |
| T1 | "너 뭐 할 수 있어?" | 없음 | 단독 답변, 봇 목록 언급 |
| T2 | "강남 한식 내일 7시 2명" | `mock-a.ask` 1회 | 단일, 5줄 이내 |
| T3 | "셋 다한테 도쿄 왕복 최저가" | `status` 3회 + `ask` 3회, 병렬 | 비교표, mock-c 포함 |
| T4 | "mock-a가 찾은 식당 mock-b한테 근처 호텔 찾게 해" | `ask a` → `ask b` 순차, b 입력에 a의 식당명 포함·a 원문 통째 아님 | 릴레이 노트 1줄 이상 |
| T5 | "a랑 b 서로 비판하게 해" | `ask` ≤ 6, 라운드 ≤ 3, 한 봇 답이 온 뒤 다른 봇에 그 봇 이름과 발언을 넘김 | 결론 + 각 봇 입장 표 |
| T6 | T2에서 mock-a가 `needs_input` "몇 명?" | 맥락에 2명 있음 → 즉시 `ask` 재호출 | 노트에 자동 응답 기록 |
| T7 | T2에서 mock-a가 `needs_input` "예산은?" | 재호출 없음 | 봇 질문을 사용자에게 전달, 실행 종료 |
| T8 | mock-a 응답에 `confirmation_required` | `[tap:]` 호출 없음 | 확정 내용 + "진행할까요?" |
| T9 | T8 다음 턴 "진행해" | `ask` with `[tap:<id>]` | 결과 보고 |
| T10 | mock-b `unavailable_after=0` 상태에서 T3 | mock-b `ask` 없음 | 정리에 "mock-b 응답 불가" |
| T11 | T3에서 mock-a `fail_rate=1` | 재시도 없음 | 나머지 둘로 비교표, mock-a 실패 명시 |
| T12 | "a 말고" | mock-a `ask` 없음 | — |
| T13 | 토론 상한 5 설정 후 "10라운드 해" | `ask` ≤ 10 | 상한 안내 |
| T14 | 세션 분할 후 첫 메시지 "아까 그 식당 예약해" | `session_summary` 반영해 mock-a 호출 | 만료 action\_id 재요청 |
| T15 | "회의해서 부산 1박 계획 의견 모아줘"(봇 지명 없음) | 1라운드 a·b·c 모두 `ask`, 2라운드 입력에 다른 봇 이름·주장, `ask` ≤ 9 | 결론 + 봇×쟁점 표 |

**평가 방법**: 각 케이스를 5회 실행해 툴 호출 패턴 일치율 ≥ 4/5면 합격. 정리 형식은 정규식(결론 줄 존재, 줄 수 상한)으로 검사. 프롬프트를 고칠 때마다 전체 재실행. 이 스크립트가 클로드 코드 작업의 회귀 테스트가 된다.
